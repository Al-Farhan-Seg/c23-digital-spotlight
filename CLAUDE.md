# C23 Digital Spotlight

## Commit authorship

Never add `Co-Authored-By: Claude` (or any AI attribution) to commit messages or PR descriptions in this repo. Commits must show only the human author. This overrides the default git-commit workflow's usual co-author trailer.

One repository, many independent static one-page websites, one Cloudflare Worker. A new site launches roughly every 7 days for a 4-week pilot, alternating between an alumna and an alumnus of Farhan Segujja's secondary-school alumni community. `c23.farhansegujja.com` (`sites/c23/`) is the campaign hub itself — the public source of truth — not a participant site.

## Repo layout

```
sites/<slug>/        source for one site (plain HTML/CSS/JS, no framework)
sites/<slug>/index.html   root page — the only HTML file
sites/<slug>/src/         its CSS/JS (src/style.css, src/main.js), referenced via ./src/...
sites/<slug>/src/assets/  images/fonts imported from JS/CSS — Vite hashes + bundles these
sites/<slug>/public/      static files copied as-is (e.g. favicon), referenced by absolute path (/file.ext)
dist/<slug>/         build output — generated, gitignored, NEVER hand-edited
scripts/build-all.mjs   builds every sites/<slug>/ into dist/<slug>/
scripts/dev.mjs         single-site dev server: npm run dev -- <slug>
worker/index.js         hostname -> slug allowlist, serves via ASSETS binding
wrangler.jsonc
vite.config.base.mjs    shared Vite config (base: '/'), merged per site
```

## Hard rules

- **Never edit another participant's `sites/<slug>/` unless explicitly asked.** Each launched site is live production for a real person; treat it as protected.
- **Never hand-edit anything in `dist/`.** It's regenerated by `npm run build`; changes will be silently overwritten.
- **Adding a site = adding a folder.** Drop a new `sites/<new-slug>/` (with an `index.html`) and it's picked up automatically by `build-all.mjs` — no build-script edits needed. You still must add one line to `HOSTNAME_TO_SLUG` in `worker/index.js` and create the DNS record — those two steps are manual and not automatable from this repo.
- **Every deploy rebuilds and includes every active site.** `npm run deploy` always runs `npm run build` first. Never deploy a partial `dist/`.
- **One-page constraint is load-bearing for participant sites, not just a style preference.** Each participant site must stay a single root `index.html` plus hashed `/assets/*` files — no secondary HTML pages/sub-routes. Cloudflare's default `html_handling: auto-trailing-slash` issues a 307 redirect for non-root, non-trailing-slash directory-style paths, and that redirect does not compose correctly with the hostname-prefix rewrite in `worker/index.js` (it would double-prefix and 404). Root-level pages with in-page anchors (`#section`) are always safe.
  - **Exception, and the only safe way to add a second page**: a flat `*.html` file directly in `sites/<slug>/` (e.g. `apply.html`, no subfolder). `build-all.mjs` picks up every root-level `*.html` file as its own build entry automatically. Because it's an exact file request with an extension, Cloudflare serves it as an individual file match — the `auto-trailing-slash` directory redirect never triggers, so it doesn't collide with the hostname-prefix rewrite. c23 (the hub) uses this for `apply.html`; do not add extra pages to a participant site without confirming it first, since the free-package promise is explicitly "one-page."
- **`base: '/'` in every site's Vite config, never `/<slug>/`.** Each site is browsed at its own subdomain root; the `/<slug>` prefix only exists inside the Worker's `ASSETS.fetch()` lookup and must never leak into built HTML/JS.
- **Existing non-campaign subdomains must never be touched or intercepted**: `www.farhansegujja.com` (GitHub Pages), `jarah.farhansegujja.com` and `roadmapsh.farhansegujja.com` (each a Cloudflare Pages custom domain). Pages custom domains take precedence over Worker routes automatically. See the `www` note below.
- **Unknown/unmapped hostnames get a hard 404 from the Worker, before `env.ASSETS` is ever consulted.** No default/catch-all site.
- **No React, backend services, databases, or new dependencies without explicit approval.** Tailwind is allowed only if it's configured through Vite and genuinely simplifies things — not a default.

## `www.farhansegujja.com`

Served by GitHub Pages via DNS, kept DNS-only (grey-clouded) in Cloudflare rather than proxied — confirmed by Farhan. Because it isn't proxied, Cloudflare Worker routes never apply to it regardless of the campaign's wildcard route, so it's inherently safe. If this ever changes (e.g. `www` gets proxied for some other reason), re-verify it has its own explicit, more-specific route before the wildcard route (`*.farhansegujja.com/*`) is live — a more specific route always wins over a wildcard.

## Adding a new weekly site — checklist

1. Scope-lock the candidate's one sentence problem, audience, and single conversion action (Day 1).
2. Create `sites/<new-slug>/` (index.html + `src/style.css` + `src/main.js`, plus `src/assets/` for imported images and `public/` for static files like a favicon) with real, given content only — never invented claims, testimonials, metrics, or prices.
3. Vary at least 4 major design dimensions from every previously launched site; compare against them explicitly; use the three-source inspiration rule.
4. Add `'<new-slug>.farhansegujja.com': '<new-slug>'` to `HOSTNAME_TO_SLUG` in `worker/index.js`.
5. Add the DNS record for the new subdomain in the Cloudflare dashboard (manual, outside this repo).
6. `npm run build`, then `wrangler dev` to smoke-test the new hostname and confirm every previously launched site still resolves.
7. `npm run deploy`.

## Anti–Vibe-Coded Quality Gate

AI output is a draft, never the finished design. Do not ship until the audience, business goal, primary CTA, brand personality, and visual rationale are explicit.

### Intent and visual system
- Every section must support trust, understanding, persuasion, or action.
- Define a restrained palette, typography scale, spacing scale, radii, borders, shadows, icon style, and interaction states before implementation.
- Every visual choice must be explainable from the brand, audience, or content.
- Reject decisions justified only as “modern,” “clean,” or “premium.”
- Compare the design against `docs/design-ledger.md` before building.

### Avoid generic AI patterns
- Do not default to purple-blue gradients, glows, glassmorphism, floating blobs, generic bento grids, oversized rounded cards, or three identical service cards.
- Do not place every content block inside a card; prefer hierarchy, whitespace, typography, imagery, and composition.
- Avoid emojis as interface icons, meaningless status dots, excessive shadows, and decorative effects without purpose.
- Do not reuse the same hero, navigation, section rhythm, CTA treatment, or motion pattern across campaign sites.

### Copy and trust
- Write specific copy explaining who is helped, what problem is solved, and why the offer matters.
- Avoid vague phrases such as “Your trusted partner,” empty superlatives, excessive hype, and repetitive AI-style wording.
- Never invent testimonials, statistics, awards, customers, prices, names, or social proof.
- Remove placeholders, dead links, sample content, and unapproved contact details before release.
- CTA labels must clearly describe the next action.

### Interaction and motion
- Every visible control must work; remove decorative controls that do nothing.
- Verify links, forms, menus, accordions, sliders, social icons, and all relevant states.
- Provide loading, success, error, disabled, hover, and focus states where applicable.
- Use animation only for hierarchy, feedback, or continuity; never animate everything.
- Respect `prefers-reduced-motion` and prevent animation-related layout shifts.

### Responsive, accessible, and performant
- Test on narrow mobile, normal mobile, tablet, laptop, and wide screens.
- Prevent overflow, overlap, clipping, unreadable text, and undersized controls.
- Use semantic HTML, labels, useful alt text, visible focus states, keyboard access, and sufficient contrast.
- Avoid unnecessary libraries, duplicated code, oversized media, and heavy effects.
- Optimise images, metadata, headings, favicon, Open Graph data, and loading.

### Mandatory release audit
1. Inspect mobile and desktop layouts.
2. Click every interactive element and verify every state.
3. Audit typography, spacing, hierarchy, icons, radii, shadows, and motion.
4. Remove generic copy, fake proof, placeholders, dead links, and purposeless decoration.
5. Confirm one obvious primary CTA and a brand-specific visual direction.
6. Check accessibility, console errors, broken assets, overflow, metadata, and performance.
7. Document at least four meaningful differences from previous campaign sites.
8. Before finishing, verify that changes work as intended — run the relevant tests, then state exactly what was tested; never claim verification that did not occur. Fix any problems found before calling the work done.

A successful build is not proof of a finished website.

## Commands

- `npm run dev -- <slug>` — local Vite dev server for one site.
- `npm run build` — builds every site in `sites/` into `dist/`.
- `npm run preview` — build, then `wrangler dev` (exercises the real Worker + ASSETS binding, not just Vite).
- `npm run deploy` — build, then `wrangler deploy`.
